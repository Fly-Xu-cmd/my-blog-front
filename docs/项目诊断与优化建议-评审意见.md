前台当前 HEAD 为 `1322780`，后台为 `fac700d`。前台 `lib/auth.ts`、`middleware.ts`、`lib/analytics.ts`、统计接口存在已有未提交修改；下文“当前代码”包括这些修改，不代表远端或已部署版本。

## 一、需要先修订的评审发现

### 1. [P1] `published: false` 不能实现原文承诺的“转私有”

原文位置：第 73—74 行（P0-3）。

当前 `app/api/notes/route.ts:33-62` 接受匿名请求，省略 `published` 时查询全部笔记，传 `published=false` 时直接查询未发布笔记。`app/api/notes/[slug]/route.ts:11-30` 只按 slug 读取，不检查发布状态。文章列表和详情有相同问题，`app/allBlogs/AllBlogsClient.tsx:14` 甚至直接请求不带发布过滤的列表。

服务端详情的 metadata 和 JSON-LD 查询也没有发布过滤，例如 `app/notes/[slug]/page.tsx:24-35,53-68`。即使从 sitemap 移除，旧链接仍然可以读取正文，笔记内容还可能出现在描述中。

因此只改同步默认值或数据库发布标志，不能封闭隐私风险。应规定：

- 匿名列表强制只查询已发布内容，忽略或拒绝匿名草稿查询。
- 匿名详情、服务端页面、metadata、JSON-LD 对未发布内容统一返回不可访问结果，通常为 404。
- 管理员预览与列表通过鉴权读取草稿；所有写操作受保护，避免匿名重新公开。
- 再进行内容审计、显式发布和必要的缓存失效处理。已被抓取的内容还需单独处理搜索引擎缓存或移除申请。

验收：有一条草稿时，匿名默认列表、`published=false` 列表、已知 slug 的 API 和页面均无法取得内容；管理员仍能编辑和预览。

### 2. [P1] 写接口清单遗漏了笔记、标签、本地上传和动态详情

原文位置：第 27—47 行（P0-1），尤其第 39 行的 `/api/notes/*`。

`SYNC_API_TOKEN` 仅用于笔记 `sync`、`delete`、`meta` 三个专用接口。普通笔记 `POST /api/notes`、`PUT/DELETE /api/notes/[slug]` 均未鉴权。另有 `POST/PUT/DELETE /api/tags`、`POST /api/upload`、`PUT/DELETE /api/dynamics/[id]` 未列入表格且没有鉴权。

照原表逐项修改仍会留下内容篡改、删除和存储滥用入口。实施清单应按每个路由和 HTTP 方法建立权限矩阵，而不是把一个目录视为已经保护。

管理写接口用管理员 JWT；同步专用接口保留独立的同步凭据。公开 PV/心跳上报属于公开功能，应考虑限流与输入限制，不能因为也是 POST 就强制管理员登录。

验收：每个管理写方法在无 token、无效 token 时拒绝；有效管理员可以操作。同步凭据与管理员凭据的用途明确。

### 3. [P1] 只加 Umi 拦截器仍会导致图片上传 401

原文位置：第 49—56 行（P0-2）。

普通业务调用使用 Umi `request`，加拦截器方向正确；但 `my-blog-admin/src/pages/post-manage/index.tsx:155-160` 的封面使用 Ant Design `Upload.action`，`src/pages/new-post/index.tsx:248-257` 也有同类入口，`src/components/MyEditor/index.tsx:27-30` 上传图片直接使用原生 `fetch`。这些请求不会经过 Umi 拦截器，当前也没有 Authorization header。

必须同时给 Upload 和原生 fetch 接入凭据，或统一使用经过鉴权封装的上传函数，并验证 token 失效时的处理。不能把“加一个拦截器”当成后台全部调用已完成适配。

验收：封面上传、粘贴/插入图片、文章 CRUD、分类标签 CRUD 在后端加鉴权后都能完成。

### 4. [P1] 补充 JSON-LD 的持久化脚本注入风险

原文未覆盖。当前 `app/posts/[slug]/page.tsx:96` 和 `app/notes/[slug]/page.tsx:79` 将 `JSON.stringify(jsonLd)` 直接写入 script 的 `dangerouslySetInnerHTML`。标题等字段来自数据库，而当前普通创建/更新接口允许匿名写入。

`JSON.stringify` 不转义 `<`；字段中的 `</script>` 能结束 HTML script 元素，再接入新的 HTML/script。`application/ld+json` 不会消除 HTML 解析层的这个问题。这使匿名内容篡改进一步成为站点持久化脚本注入风险。即使补上管理员鉴权，仍应安全序列化内容。

建议对嵌入 HTML 的 JSON 使用安全序列化，至少将 `<` 替换成字面量 `\u003c`，并检查两类详情页。该判断来自源码，未对线上页面注入或执行攻击载荷。

验收：包含 script 结束标签的测试标题只能作为 JSON 数据出现，无法创建额外 HTML 元素或执行脚本。

### 5. [P2] 90 天清理方案会破坏现有累计统计

原文位置：第 76—81 行（P0-4）。

缺乏保留策略属实，但单凭容量增长不能与匿名删文、泄露私密内容列为同等紧急。更具体的当前压力点是每次心跳都执行全表 PV 计数和 UV 去重统计：`app/api/analytics/heartbeat/route.ts:27-31`；客户端正常每 30 秒心跳一次。

当前 `site`、`heartbeat`、`views`、`stats` 均从原始 PageView 读取。只加日聚合并删除旧明细，会让全站累计和文章累计阅读量退化为保留窗口内的统计。日 UV 不能直接相加得到累计 UV：同一访客两天访问会被计为两人。

应先定义指标语义、累计与分组的存储结构，改造读取端，完成历史回填和聚合幂等校验，最后才清理明细。写入路径可继续落明细，但清理任务、读取路径和 UV 去重方案不能省略；可先缓存心跳返回的累计值并对公开上报限流。

验收：归档前后累计 PV、单篇累计阅读量保持一致；跨天重复访客按约定的 UV 口径统计；清理和聚合重复执行不重计。

### 6. [P2] 列表去全文不能直接套用“只留 excerpt”

原文位置：第 103—113 行（P1-2）。

列表返回全部正文、没有分页的判断成立。首页传了 `current/size`，后台传了 `current/pageSize`，但文章 GET 完全没有解析分页参数。

不过 Note 模型没有 excerpt，`app/notes/NotesClient.tsx:221-223` 直接执行 `note.content.replace(...)` 生成摘要；后台 `post-manage/index.tsx:104-110` 打开编辑表单也直接使用列表的 `record.content`。直接移除 content 会导致笔记列表报错、后台编辑没有正文，随后保存可能造成内容丢失。

应区分公开列表、管理员列表、完整详情的返回类型；为笔记生成摘要，后台编辑按需读取完整详情，同时实现服务端搜索、分页和总数，再删除列表正文。

## 三、内容模型建议的修订

Series 独立建表、内容类型使用 Note.kind、暂缓 Post/Note 合并，都是合理的可选方向；不应把没有 Series/publishedAt 描述成所有内容都无法保存草稿。Post 和 Note 已有 published，Dynamic 才没有发布开关。

实施前还需补全：

1. **Dynamic 发布控制**：原文提到问题，但建议 schema 和迁移步骤都漏了 Dynamic.published。增加开关时，已有动态若继续公开应显式回填，避免使用 false 默认值隐藏全部历史动态；同步修改公开查询和后台表单。
2. **发布时间语义**：建议表示首次发布时刻，首次发布时写入，隐藏后保留，重新发布不改写。“未发布为 null”应改为“从未发布为 null”。后台“创建时间”列仍显示 createdAt；发布趋势与创建趋势分开，不能机械替换所有日期。
3. **系列序号与约束**：seriesOrder 决定系列阅读顺序，publishedAt 决定发布时间线，不存在技术上必须同时迁移的依赖。单人也可能开两个页面、重试请求；建议用非空系列与序号的数据库唯一约束防抢号，用事务安排重排，同时校验序号为正和系列存在。系列页与上下篇导航只能暴露已发布文章。
4. **同步字段契约**：如果 sync 接受 published/kind，必须明确遗漏字段时如何保留现有值；当前只按 syncId/hash 跳过会吞掉正文没变的发布状态、kind、分类和标签变更。内容 hash 相同不等于全部元数据相同。
5. **部署兼容**：新增可空字段、回填、应用读取切换、删除旧索引可以属于同一功能交付，但不能把“必须一次做完”当作部署安全策略。正式迁移需验证旧/新代码兼容、备份恢复及回填的幂等性；createdAt 只是现有历史文章发布日期的近似来源。

## 四、保留的诊断与执行顺序

源码支持以下判断：管理写接口缺鉴权，普通业务请求缺 token；文章/笔记正文依赖客户端获取；列表全文且无文章分页；同步新笔记强制公开；Dynamic 没有发布开关；中文 slug 被过滤；首页缺介绍且请求串行；锚点依赖固定延时；旧文档、迁移遗留和仓库中的本地工具配置需要整理。

建议按风险和依赖顺序推进：

1. 管理写鉴权及全部后台请求适配，匿名草稿读取隔离，安全 JSON-LD 序列化；完成敏感内容审计和显式发布契约。
2. 公开详情正文首屏渲染，未发布/不存在页面正确返回 404；列表摘要、分页、按需详情和搜索。
3. 统计缓存与限流；有证据需要时再实施保留/归档，确保累计值与 UV 口径不丢失。
4. 根据博客定位推进 Series、首次发布时间、Dynamic 草稿、Note.kind，再决定分类、RSS、标签聚合与作品集页面。

上述验收项是后续实现的要求，未在本次评审中执行。此次完成源码核对和诊断方案评审，没有运行全量构建、迁移或线上业务验收。
